# Local MLflow study archive — 2026-09-30

## Actual integration

MLflow is now called by the workbench's real study-save path, after the immutable
Workspace record has been committed. It is optional and off by default:

```bash
python -m pip install -e '.[mlflow]'
python -m invest.server --data-dir .invest --track-experiments
```

The source-Python worker uses the installed MLflow SDK. Runtime validation uses
MLflow **3.16.1** on synthetic studies. The optional extra is pinned to that
version (upstream Requires-Python: >=3.10, compatible with Invest); an existing
different SDK version reports `unsupported_mlflow_version` without importing it. The existing `MLflowExperimentTracker`
fluent adapter and `create_mlflow_tracker()` remain compatible; the workbench
uses the separate `LocalMLflowArchive` and never calls the fluent API.

The worker is intentionally not embedded in the frozen Windows executable.
If enabled from a frozen build it reports `source_python_required` while still
saving the study. This change does not claim portable-EXE or human desktop acceptance.

## Data and failure contract

- `POST /api/workbench/study` saves the authoritative study first. When tracking
  is enabled, its existing document fields are preserved and a response-only
  `tracking` object reports `archived` or `failed`. A tracking failure still
  returns HTTP 200 for the successful study save. Default-off responses are
  unchanged. Document downloads always return the immutable record without
  this transient status.
- `POST /api/workbench/track-study` with `{"study_id":"<saved ID>"}` retries the
  derivative archive without re-running research. It uses the same host,
  origin, CSRF and nonblocking study-lock guards. When disabled it reports
  `disabled`. Invalid or missing saved studies are rejected.
- Both known study schema/mode pairs are supported: chronological slices and
  the PR #49 walk-forward study. Payload and protocol schemas must agree;
  unknown schemas/modes and opened frozen holdouts are rejected.
- One run is associated with each content-addressed study ID. A complete retry
  verifies the stored study bytes and reuses the existing run without adding
  metrics. A partial failure marks the run failed; retry resumes that same run
  and does not duplicate existing summary metrics. Duplicate or mismatched run
  identities and missing/tampered completed artifacts fail closed.
- The client records dataset, protocol and code identities as tags; symbol,
  cash, mode, parameter budget and warmup as parameters; and the four study
  summary counts and successful-case returns, drawdown and fees as metrics.
  Each case index has a descriptor with candidate, cost, period/fold and window;
  indices are local to a protocol and must not be assumed aligned across
  different protocols. A bounded canonical `study.json` contains the
  exact saved record, including all candidate/cost/period configurations,
  outcomes, failures, replay results and limitations. No holdings, journal,
  private notes, credentials or environment dump are collected.
- Failed tracking status is returned only to the caller, not written into the
  immutable study. The saved document remains downloadable even if MLflow is
  absent, times out, has corrupt metadata or cannot write.

## Strictly local operation

The configured data directory contains `mlflow/tracking.sqlite`,
`mlflow/archive-lock.sqlite` and `mlflow/artifacts/`. Both `tracking_uri` and
`registry_uri` are explicit local SQLite URIs. Registry operations are not used.
The worker ignores inherited `MLFLOW_*` variables and sets
`MLFLOW_DISABLE_TELEMETRY=true` and `DO_NOT_TRACK=true` **before SDK import**.
It checks that the telemetry client is absent, logs synchronously, and has no
active global run, autologging, tracing, system-metrics collection, model
registry, MLflow server or remote service. A Python socket audit guard provides
additional protection against accidental SDK networking; it is not an OS sandbox.

Existing experiment and run artifact locations must be absolute local file
URIs beneath the configured artifact directory. Remote schemes, UNC hosts,
relative paths, sibling paths, symlink escapes, SQLite URI delimiter paths,
redirects to a different local run, and changes just before artifact
writes are rejected. Local SQLite transaction locking serializes archive writes
across separate Invest server processes. As with the existing workspace, a
concurrent malicious process with access to the user's private directory is
outside this protection boundary.

The lock wait is bounded to 30 seconds inside the unchanged 45-second worker
deadline. This permits a competing process to finish a cold database setup or
artifact commit, rather than failing at the former 10-second boundary. A lock
that remains busy reports `archive_busy` without exposing paths or SQLite
messages; the saved study is still authoritative and can be retried. Tests
retain the two-concurrent-worker/single-run assertion and additionally hold a
real SQLite writer lock for 12 seconds before releasing it to the actual SDK.

A short-lived Python subprocess bounds each attempt to 45 seconds and releases
MLflow's cached database handles at exit, including on Windows. The worker emits
only a small status response; SDK logs and raw exceptions are not returned to
HTTP clients. A crash or timeout may leave an incomplete derivative run that can
be retried from the saved study. Source Python and its MLflow extra must remain
available when tracking is enabled.

## Backups and restoration

The standard private backup continues to contain `paper.sqlite`, `state.sqlite`
and its existing manifest. These include every authoritative saved study and
its content identity. The **derivative MLflow database and artifacts are not
part of that backup**. `/api/workbench/status` explicitly exposes this fact.
After restoration, enable tracking and call `/api/workbench/track-study` for
saved IDs to recreate their archives. MLflow run IDs are local derivative IDs
and can change on reconstruction; Invest study/protocol/dataset/code identities
do not change. This feature does not broaden the existing backup format or
claim that an external MLflow archive is backed up.

## Verification scope

`tests/test_mlflow_local.py` uses actual loopback HTTP and the real SDK for
save → local run/artifact → SDK readback → repeat, failed writes and recovery,
inherited remote environment variables, malicious backend artifact locations,
backup reconstruction, and cross-platform handle release. Separate tests cover
default-off no-import/no-worker behavior, missing SDK, timeout, HTTP guards and
frozen-executable refusal. `.github/workflows/mlflow-local.yml` runs this on
Ubuntu and Windows with Python 3.11 and 3.12. All research fixtures are synthetic;
none of these checks prove real-market validity or trading performance.
